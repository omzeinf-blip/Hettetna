# الأمان

## النموذج باختصار

| الطبقة | الإجراء |
|---|---|
| المفاتيح | المفتاح السري يُقرأ على الخادم فقط ولا يصل للمتصفح. لا أسرار في الكود أو الـ ZIP |
| زوار الموقع | قراءة العقارات المنشورة غير التجريبية فقط. لا قراءة ولا كتابة على الاستفسارات |
| إرسال الاستفسار | عبر الخادم فقط: تحقق، حقل مصيدة، فحص Origin، حد 5 طلبات/10 دقائق لكل زائر (مخزَّن في قاعدة البيانات بتجزئة مفتاحية للـ IP) |
| لوحة الإدارة | كل صفحة وإجراء يتحقق من الجلسة عبر Supabase Auth **وأن المستخدم موظف فعّال** في الخادم، وقاعدة البيانات تفرض RLS مرة ثانية بنفس رمز المستخدم |
| الحسابات | لا تسجيل عام. وجود حساب لا يمنح صلاحية دون صف في `staff_profiles` |
| الملفات | رفع الصور للموظفين فقط، فحص النوع من محتوى الملف (وليس الاسم)، حد 4 ميجا، مخزن بأنواع محددة |
| الكوكيز | `HttpOnly` و`SameSite=Lax` و`Secure` في الإنتاج |
| الواجهة | ترويسات أمان (`nosniff`, `X-Frame-Options`, `Referrer-Policy`, `HSTS`)، ومنع فهرسة `/admin` |

## اختبارات الصلاحيات بعد تشغيل الـ Migration

شغّلها في **SQL Editor**، كل اختبار على حدة. كلها لا تغيّر بيانات (تتراجع تلقائيًا).

```sql
-- 1) الزائر لا يقرأ الاستفسارات. المتوقع: خطأ permission denied
begin; set local role anon; select * from public.inquiries limit 1; rollback;

-- 2) الزائر لا يكتب استفسارًا مباشرة. المتوقع: خطأ permission denied
begin; set local role anon;
insert into public.inquiries (kind,name,phone,consent) values ('contact','اختبار','01000000000',true); rollback;

-- 3) الزائر لا يرى المسودات. المتوقع: 0
begin; set local role anon; select count(*) from public.properties where published = false; rollback;

-- 4) الزائر لا يقرأ أعمدة التدقيق (معرّفات الموظفين). المتوقع: permission denied
begin; set local role anon; select created_by from public.properties limit 1; rollback;

-- 5) الزائر لا يقرأ جدول الموظفين ولا عدّادات الحماية. المتوقع: permission denied لكل منهما
begin; set local role anon; select * from public.staff_profiles limit 1; rollback;
begin; set local role anon; select * from public.rate_limit_hits limit 1; rollback;

-- 6) الزائر لا يعدّل بيانات التواصل. المتوقع: permission denied
begin; set local role anon; update public.contact_settings set phone = 'x'; rollback;

-- 7) مستخدم مسجّل لكنه ليس موظفًا لا يرى شيئًا إداريًا. المتوقع: 0 صفوف
begin; set local role authenticated;
select set_config('request.jwt.claims','{"sub":"00000000-0000-4000-8000-000000000000","role":"authenticated"}',true);
select count(*) from public.inquiries; rollback;
```

وجرّب من الموقع نفسه:
- فتح `/admin/properties` بدون تسجيل دخول ← تحويل إلى صفحة الدخول.
- حساب Supabase ليس له صف في `staff_profiles` ← لا يستطيع الدخول.
- حساب `agent` ← لا يرى «الإعدادات» ولا زر الحذف.

## ما لا يغطيه المشروع

- النسخ الاحتياطي وسياسة الاحتفاظ بالبيانات: تضبطها من Supabase ومن سياستك الداخلية.
- المصادقة الثنائية (MFA) للمديرين: متاحة في Supabase ويُنصح بتفعيلها لاحقًا.
- مراجعة نص سياسة الخصوصية قانونيًا.

## ملاحظات فاحص الأمان في Supabase (Security Advisor)

بعد تطبيق الـ Migration على مشروعك (2026-10-25) ظهرت ملاحظتان، وكلتاهما **مقصودة**:

| الملاحظة | لماذا هي مقصودة |
|---|---|
| `rate_limit_hits`: RLS مفعّل بدون سياسات (INFO) | الجدول لا يقرؤه أو يكتب فيه إلا الخادم بالمفتاح السري. غياب السياسات يعني منع الجميع الآخرين، وهذا المطلوب |
| `is_staff()` و`is_admin()`: دوال SECURITY DEFINER قابلة للتنفيذ من المستخدمين المسجلين (WARN) | سياسات الأمان تستدعيها بصلاحيات المستخدم نفسه، فلا بد من السماح بتنفيذها. تُرجع قيمة صح/خطأ عن حساب المستخدم نفسه فقط، ولا تكشف بيانات غيره، وهي غير متاحة للزوار (anon) |

تحسين اختياري لاحقًا: نقل الدالتين إلى مخطط غير معروض عبر الـ API لإزالة التحذير. يتطلب تعديل السياسات، فلا يُنفَّذ إلا بموافقتك.

## حالة قاعدة بيانات مشروعك

نُفّذت اختبارات الصلاحيات أعلاه (وغيرها، 36 فحصًا) على قاعدتك الفعلية داخل معاملة تتراجع بالكامل، ونجحت كلها: الزائر لا يقرأ أو يكتب الاستفسارات، والمستخدم غير الموظف لا يرى شيئًا إداريًا، والموظف لا يحذف ولا يرقّي نفسه، والموظف الموقوف يفقد صلاحياته فورًا.
