# تحديث الاعتماديات الأمنية (Next.js 15 / sharp / postcss)

## الحالة الحالية (مُتحقَّق منها من `package-lock.json` و`npm ls`)

| الحزمة | الإصدار الحالي | ملاحظة |
|---|---|---|
| `next` | 15.5.9 | مثبّت بالرقم الحرفي في `package.json` |
| `eslint-config-next` | 15.5.9 | يجب أن يطابق إصدار `next` |
| `react` / `react-dom` | 19.1.0 | يلبّيان شرط Next (`^19.0.0`) |
| `sharp` | 0.34.5 | **ليس اعتمادية مباشرة**: اعتمادية اختيارية من Next بنطاق `^0.34.3` |
| `postcss` | 8.5.31 (جذري، من Tailwind) + **8.4.31 داخل `node_modules/next/node_modules/postcss`** | Next 15.5.9 يثبّت `postcss@8.4.31` حرفيًا |

### لماذا لا يكفي `npm install sharp@0.35.5`؟
نطاق Next لـ sharp هو `^0.34.3`، ولا يسمح بـ0.35.x (في سلسلة 0.x الرقم الأوسط يعامل كإصدار رئيسي). فتثبيتها كاعتمادية مباشرة يُبقي نسخة 0.34.x مخبأة داخل `node_modules/next/node_modules/` وNext سيحمّلها هي. لذلك يتحقق السكربت من **النسخة التي يحمّلها Next فعليًا**، ولا يضيف `override` إلا إذا لزم، ولـ sharp وحدها.

## ما يقوله تقرير `npm audit` الذي أرسلته

| الحزمة | الشدة | المسار | النطاق المتأثر | الحل |
|---|---|---|---|---|
| `next` | حرجة (30+ تنبيهًا) | `node_modules/next` | حتى 16.3.0-preview | `next@15.5.28` |
| `postcss` | عالية | `node_modules/next/node_modules/postcss` | `<=8.5.22` | يأتي مع تحديث Next (وإلا override مقيّد، انظر أدناه) |
| `sharp` | عالية | `node_modules/sharp` | `<=0.35.5-rc.1` | `0.35.5` أو أحدث |

- الحل الذي يقترحه npm هو `next@15.5.28` وهو **ضمن سلسلة 15.x** (عبارة «خارج النطاق المذكور» سببها أن `package.json` يثبّت `15.5.9` حرفيًا، وليست ترقية رئيسية). لا حاجة لـ Next 16.
- مع ذلك **لا تستخدم `npm audit fix --force`**: لا يُحدّث `eslint-config-next` ليطابق Next، ولا يتحقق من sharp الذي يحمّله Next فعليًا، ولا يحتفظ بنسخة احتياطية ولا يختبر البناء. السكربت يفعل ذلك كله.
- postcss الجذري عندك 8.5.31 (سليم). المشكلة في النسخة 8.4.31 المثبّتة حرفيًا داخل Next؛ فإن لم تعالجها نسخة Next الجديدة يضيف السكربت `overrides: { "next": { "postcss": "8.5.31" } }` **فقط حينها**، وبنسخة موجودة أصلًا في القفل.

### ما يمسّ موقعك من هذه التنبيهات (قراءة للعناوين مقابل الكود، لا بديل عن التحديث)

| محور التنبيهات | وضع المشروع |
|---|---|
| تجاوز Middleware | الـ middleware عندنا لا يمنح صلاحية: كل صفحة وإجراء وAPI في الإدارة يتحقق من الجلسة ودور الموظف على الخادم، وقاعدة البيانات تفرض RLS أيضًا |
| Server Actions / Server Functions | إجراءات الإدارة تتحقق من الصلاحية داخلها؛ نموذج الدخول عام بطبيعته وعليه حد للمحاولات |
| محسّن الصور (DoS / RCE عبر AVIF وSVG) | صيغ الصور على الإعداد الافتراضي (WebP) وSVG غير مفعّل، والمصادر الخارجية مضيفان فقط (Unsplash وتخزين مشروعك)، ورفع الصور للموظفين فقط مع فحص نوع الملف من محتواه. هذا يقلل التعرض ولا يلغي ضرورة التحديث |
| تسميم ذاكرة التخزين المؤقت (SSG / ISR) | **ذو صلة**: الموقع يستخدم ISR للصفحات العامة، ولذلك التحديث ضروري |
| rewrites وSSRF وWebSocket والخادم المخصص | غير مستخدمة في المشروع |
| CSP nonce و`beforeInteractive` وCache Components وصفحات i18n وEdge runtime | غير مستخدمة في المشروع |
| RCE على خوادم ويندوز | الإنتاج على Vercel (لينكس)؛ جهازك المحلي ويندوز لأغراض التطوير فقط |

## لماذا لم يُنفَّذ التحديث داخل المحادثة؟
بيئة المساعد بلا اتصال بسجل npm، فلا يعمل `npm install` ولا `npm audit` ولا `npm run build`. وتعديل `package.json` دون إعادة توليد `package-lock.json` يتركهما غير متطابقين ويكسر `npm ci` على الاستضافة. لذلك جُهّز سكربت آمن تشغّله أنت على جهازك. لم يُتحقق من وجود `next@15.5.28` ولا `sharp@0.35.5` في السجل؛ إن لم يوجدا يظهر خطأ `ETARGET` ويُرشدك السكربت لعرض المتاح بالأمر `npm view next@15 version`.

## التشغيل

```bash
# 1) اختياري لكنه أفضل: احفظ حالتك الحالية في git (في Windows PowerShell نفّذ السطرين منفصلين)
git add -A
git commit -m "قبل تحديث الاعتماديات"

# 2) تجربة بدون أي تغيير
npm run deps:update -- --dry-run

# 3) التنفيذ، مع استعادة تلقائية إذا فشل TypeScript أو البناء
npm run deps:update -- --restore-on-failure
```

خيارات: `--next 15.5.30` (لتغيير الإصدار المطلوب، ويجب أن يبقى 15.x)، `--sharp 0.35.6`، `--postcss-min 8.5.23`، `--skip-build`.

## ماذا يفعل السكربت بالترتيب؟

1. **يرفض** أي إصدار Next خارج 15.x. **لا** يستخدم `npm audit fix` ولا `--force`.
2. يأخذ **نسخة احتياطية** من `package.json` و`package-lock.json` في `.dependency-backup/<التاريخ>/` ويسجّل الإصدارات قبل التحديث.
3. يثبّت `next` و`eslint-config-next` بنفس الإصدار، و`react`/`react-dom` من 19.1.x، بأرقام حرفية.
4. يتحقق من إصدار **sharp الذي يحمّله Next فعليًا**، ويضيف `overrides.sharp` عند الحاجة فقط ثم يعيد التثبيت ويتحقق مجددًا.
5. يفحص **postcss**: إن بقيت نسخة ≤ 8.5.22 يضيف override مقيّدًا بـ `next` إلى نسخة موجودة أصلًا في القفل (وإلا لا يفعل شيئًا ولا يخمّن رقمًا).
6. يشغّل `npm audit --json` ويطبع لكل ثغرة: الحزمة والمسار والنطاق المتأثر والحل الآمن، ويضع علامة «لا تطبّقه دون مراجعة» على أي حل يتطلب ترقية رئيسية.
7. يشغّل: `npm ls`، `npx tsc --noEmit`، `npm run lint`، `npm test`، `npm run build`، ويعرض نتيجة كل فحص.
8. يكتب تقريرًا `dependency-update-report.md` بالإصدارات قبل وبعد والنتائج والثغرات المتبقية.

## بعد التشغيل

- إن نجح كل شيء: ارفع `package.json` و`package-lock.json` **معًا** في نفس الـ commit.
- المتوقع بعد النجاح: `npm audit` يعرض `found 0 vulnerabilities`. إن بقي أي تنبيه فأرسل لي `dependency-update-report.md` أو خرج `npm audit` الجديد.
- لا تشغّل `npm audit fix --force`: قد يرقّيك إلى Next 16 ويكسر المشروع.

## الرجوع

انسخ `package.json` و`package-lock.json` من مجلد `.dependency-backup/<التاريخ>/` فوق الملفات الحالية ثم شغّل `npm ci`. (نسخة المسلَّم الأصلية موجودة أيضًا مع المساعد: `dependency-backup-before/` ومعها SHA256SUMS.)

## ملاحظة عن البناء

`npm run build` يحتاج اتصالًا بالإنترنت (خطوط Google) وحزمة SWC المناسبة لنظامك؛ ويعمل بدون مفاتيح Supabase (تظهر الصفحات بحالة التحميل الاحتياطية).
